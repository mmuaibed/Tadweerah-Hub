## Context (Current State)

M4.5 is complete and frozen:
- Listing → Offers → Reject (with reason) → Accept (with acceptance_reason if below highest) → Auto-reject others → Listing closes
- UI and DB invariants are validated

Problem: After acceptance, the platform reaches a dead end.
There is no post-acceptance workflow to complete a real transaction.

---

## Goal

Design and validate a minimum viable transaction completion flow (MVP-light) that:
- Works in the Saudi waste trading context
- Supports BOTH:
  1) Fixed lump-sum deals
  2) Price-per-unit / weight-based deals
- Enables a real, practical trade to be completed
- Does NOT overbuild (no full logistics or payment systems)
- Does NOT destabilize M4.5

---

## Proposed MVP Transaction Flow

### 0) Accepted (Existing)
- Offer accepted
- Listing closed
- Other offers auto-rejected

---

### 1) Settlement Type (NEW — must be explicit)
Each accepted deal must have:
- settlement_type = "fixed" | "actual_quantity"

Source:
- Either from the accepted offer
- Or inferred if offer already has unit pricing

---

### 2) Actual Quantity / Finalization Step (NEW — conditional)

IF settlement_type = "fixed":
- final_amount = accepted_offer_amount
- No quantity input required

IF settlement_type = "actual_quantity":
- Require recording:
  - actual_quantity (number)
  - optional unit (ton/kg)
  - optional evidence (image/document)
- System calculates:
  - final_amount = price_per_unit × actual_quantity

---

### 3) Final Amount Visibility (NEW)
- Both producer and buyer must see:
  - settlement_type
  - unit price (if applicable)
  - actual_quantity (if applicable)
  - final_amount
- This must be read-only once confirmed

---

### 4) Payment Proof (MVP — offline)
- Buyer uploads:
  - payment_proof (image/file)
- Status → "payment_submitted"

---

### 5) Payment Confirmation
- Producer confirms receipt
- Status → "payment_confirmed"

---

### 6) Handover to Carrier (Lightweight)
- Producer records:
  - carrier_name (required)
  - optional phone
  - optional notes
- Status → "handed_over"

---

### 7) Final Receipt Confirmation
- Buyer confirms material received
- Status → "received"

---

### 8) Transaction Close
- Status → "completed"
- Immutable end state

---

## Key Requirements

- Must remain MVP-light (no full logistics engine, no payment gateway)
- Must be auditable (who did what, when)
- Must avoid ambiguity in final price
- Must not break M4.5 flows or invariants
